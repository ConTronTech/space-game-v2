CONTEXT: the user is going to keep hitting "weird quirks" while developing (they already found the wheel first-value bug, the orbit lock plane collapsing through a planet's centre, a station pole that should not be there, etc. - all found by PLAYING, not by reading logs) and wants a real debugging tool, not just more log lines. The live performance profiler (F3/F4/F5, docs/PERFORMANCE.md, package/engine/profiler_live.{h,cpp}, package/modules/core/profiler_overlay/) is the closest existing thing and the model to follow: always-on lightweight recording, a toggle-key overlay, a dump-to-file for sharing a repro. Build the GAMEPLAY/STATE equivalent of that, generalised so any module can plug debug info into it without the debugger module knowing anything about that module (the same "optional service" pattern used everywhere else in this codebase: docking exposes IDocking, weapons expose ICombat, etc. - this module exposes ONE registration service that other modules call INTO).

DESIGN:
1. New module package/modules/core/debugger/ (name "core/debugger"; requires core/input_handler, core/render_engine, core/ui_handler; everything it inspects is OPTIONAL - the debugger must never crash or error when a module it could show is absent). Provides `core::IDebug` in debugger_api.h:
   - `void watch(const std::string& name, std::function<std::string()> getter)` - any module registers a named live value (e.g. "gravity.dominant", "ship.speed", "orbit.state"); the debugger polls these only while its own overlay is open (never per-frame when closed: zero cost when the tool is not in use, exactly like the live profiler's overlay-only cost).
   - `void drawHook(const std::string& name, std::function<void(core::RenderEngine&)> fn)` - a named toggleable world-space debug draw (vectors, spheres, predicted paths); the debugger calls these ONLY for hooks the player has switched on, inside its own render pass (so ownership of GL state is the debugger's, not the caller's: document exactly what state a hook may assume/must not change, following the same discipline as every other render pass in this codebase - push/pop only what you touch).
   - `void unwatch(name)` / `void removeDrawHook(name)` for clean module shutdown (a module that unregisters on its own `shutdown()`, same lifecycle as `addPanel`/`removePanel`).
   - A small read-only `pickNearest(worldPos, maxRange) -> optional id/kind/name` is NOT required (too much per-module coupling); instead modules that want to be "clickable" register their OWN entries in the watch list already (simplest, decoupled, matches the rest of the codebase's style).
2. OVERLAY (key F6 = `toggle_debugger`; add to config/input/default.json + docs/INPUT.md + docs/QUICKSTART.md; a second key F7 = `toggle_debug_draws` shows/hides all active draw hooks without closing the panel): a corner panel (reuse core/ui_handler glass/bar/button/tabs widgets, small quads only, cached text, same discipline as the live profiler overlay: near-zero cost while open, ZERO cost while closed) listing every registered watch value updated a few times a second (not per frame: batch at e.g. 4 Hz like the radar/asteroid caches already do elsewhere in this codebase), grouped by the module-supplied prefix before the first '.' (so "gravity.dominant", "gravity.accel" group under "gravity"); each draw-hook name gets a toggle checkbox in the panel. A free-fly DEBUG CAMERA is NOT required for this pass (flag it as a documented follow-up, out of scope: it would need its own camera mode and this task is already large) - instead the existing chase/cockpit toggle (V) plus the panel is enough for a first version; say so explicitly in the report.
3. EVENT LOG VIEWER: a scrollable panel (toggle with the F6 panel's own tab, reuse tabs()) of the last N (e.g. 200) engine events the game ALREADY emits (subscribe generically is not possible without a type-erased event bus hook - check engine::EventBus's actual API first and report what it supports; if there is no generic "log every event" hook, do NOT invent one in the engine for this task - instead have common modules (ship_core: DamageTaken/Died/Respawned; docking: Docked/Undocked; combat: WeaponChanged/Overheated/ProjectileHit; mining: OreMined/CargoFull; stations/orbit_lock similarly) each push one line into the debugger's log via a tiny `void logEvent(const std::string& line)` on IDebug when they already emit their own event - this is a FEW one-line additions inside modules whose files you do NOT otherwise own: list EXACTLY which files/lines you propose touching for this (it should be a single `if (auto* dbg = ...) dbg->logEvent(...)` right next to each existing `eng.events.emit(...)` call) and treat it as a "needs decision" per file if the ownership rule is unclear - prefer doing it only in files this task DOES own, and for everything else, write the exact one-line diff in the report for the coordinator to apply by hand instead of editing modules outside your ownership without asking.
4. DUMP (key F8 = `dump_debug_state`): writes `logs/debug_state.txt` - a snapshot of every current watch value plus the last 200 log lines plus (if the live profiler's data is reachable through a service, optional) a one-line pointer telling the user to also press F5 for a performance snapshot. This is what the user pastes back after a "weird quirk". Make it self-explanatory the same way `logs/profile_live.txt` is (docs/PERFORMANCE.md's own advice: "the file must be self-explanatory").
5. PHYSICS-SPECIFIC WATCHES/DRAWS YOU BUILD YOURSELF (generic, not tied to the gravity task landing first or not): a "physics" tab always available (no optional dependency needed) showing the ship's own position/velocity/speed (from ship::IShip if present) and, if core::IPhysics exposes anything queryable cheaply, active collision body count; a toggleable draw hook for the ship's velocity vector (a short world-space line from the ship, camera-relative like every other world-space draw in this codebase - copy the pattern from ship/orbit_lock's guide rendering or combat/weapons' lock bracket, both already do camera-relative double->float world-space lines cheaply).
