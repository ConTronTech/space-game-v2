TASK 7.1 - double-precision ship/physics positions (foundation for realistic-scale rescale). REPORT EARLY AND OFTEN: this is a higher-risk, foundational task - send a heartbeat after the call-site audit (item 1), after ship_core's internal change (item 2), and after each subsequent item. Do not wait to finish everything before reporting. If you hit a design fork not covered below, STOP and report "needs decision" rather than guessing - this task is deliberately not run at low effort because a subtle bug here corrupts flight/physics everywhere.

WHY: the user wants the star system rescaled to REAL astronomical distances (sun ~696,000 km radius, planets thousands of km, orbits tens of millions to billions of meters apart) instead of today's compressed ~1-2 km sun / ~30-80 km planet spacing. Before ANY of that rescale happens, a real architectural problem must be fixed: `ship_core`'s live position (`pos_`, integrated every fixed step as `pos_ += vel_ * dt`) is stored as `engine::Vec3` - **float**. At realistic distances (millions to billions of meters from the world origin), float32 has only ~7 significant decimal digits: at 4.5e9 (Neptune-orbit scale) one float ULP is already ~536 meters. That is catastrophic for flight, docking, collision and combat - the ship's own position would visibly jitter/snap in hundred-meter steps. `world::Vec3d` (double) is ALREADY used for planet/asteroid/station positions and rendered correctly via the existing "camera-relative" pattern (subtract in double, cast only the small remainder to float for GL) - see how `world/star_system`, `world/atmosphere` and `world/asteroids` already do this (grep `camera-relative` in those files). The gap is specifically that the SHIP's own authoritative position (and, downstream, `core/physics_world`'s body positions, both currently float) is not part of that double-precision discipline yet, so it poisons every calculation that combines it with a body's double position (gravity, orbit_lock, docking, and the camera anchor that every "camera-relative" render pass ultimately derives from - confirmed by grep: `world/star_system` recovers "camera position" from the GL view matrix, which was itself built from the ship's float pose).

THIS TASK IS PLUMBING ONLY. Do NOT touch any world-scale numbers (sun/planet radii, orbit distances, warp speeds, draw distances) - that is separate, future work that depends on this landing solid first. The ENTIRE point of this task is that gameplay at TODAY's scale must be provably unchanged (a pure precision upgrade, zero behaviour change at current distances), while ALSO now being correct far from the origin (which nothing exercises today, but the rescale will).

CHANGE:
1. **Audit first, report before touching code.** Every consumer of `IShip::position()`/`velocity()` (confirmed by grep: `fx/particles`, `gameplay/mining`, `ship/cockpit` (`hud_screens.cpp`), `ship/docking`, `ship/gravity`, `ship/orbit_lock`, `ship/warp_drive`, `ui/system_map`, `world/anomalies`, `world/asteroids` - re-grep yourself, this list may be incomplete) and every caller of `core::IPhysics::addBody/setBody/teleport/query` (the position parameters are all `engine::Vec3`, float). For each, classify it: (a) needs TRUE absolute precision at huge distance (gravity's body-relative math, orbit_lock's plane/guide math, docking's fine hold-position math, the camera anchor powering every camera-relative render pass) vs (b) only ever computes something already SHIP-RELATIVE and small (a HUD readout of "nearby object at N meters", a particle spawn offset, a mining chunk a few dozen meters from the ship, a weapon projectile fired near the ship) where float precision remains fine as long as the RELATIVE offset itself is computed correctly (see item 4). Report this classification in your first heartbeat.
2. **`ship_core`'s internal position becomes double.** Change the internal `pos_` (and the integration `pos_ += vel_ * dt`) to `world::Vec3d` (reuse the existing type - do not invent a second one; check whether `world::Vec3d` is easily includable from `ship_core` without a layering violation, and if not, look at whether it belongs promoted to `engine::` instead - your call, document the reasoning either way). Velocity can stay float (`engine::Vec3`) - velocities are always modest, m/s-scale; only POSITION accumulates precision loss over distance. Add a new accessor to `IShip` (e.g. `world::Vec3d positionD() const` - name it sensibly) that returns the true double position, alongside the EXISTING float `position()` (keep it - it becomes an intentional approximation for cosmetic/local-relative callers, see item 4; do not remove it, do not break its signature, existing callers must keep compiling). `setPose`/`teleport`/save-load (`core/save_system` persistence of ship position) need updating too so a save file round-trips the full double precision (check `ship_core.cpp`'s `save()`/`load()` - currently likely writes float JSON numbers; JSON numbers can hold double precision fine, just make sure the read/write path doesn't truncate through an intermediate float).
3. **`core/physics_world` positions become double** for the same reason (a collision sweep test between the ship and something registered nearby needs accurate SUB-METER relative precision even when both objects' absolute coordinates are huge). Extend `core::IPhysics`'s position parameters (`addBody`, `setBody`, `teleport`, `query`) to double (`world::Vec3d` or equivalent) - this is a real API signature change, so EVERY caller (`ship_core` itself, `gameplay/mining`'s chunks, `combat/weapons`' projectiles/missiles, `world/asteroids`' physics pool, `world/stations`) needs updating to pass/receive double positions. If this turns out too invasive to do safely in this task's time budget, an acceptable interim alternative (state which you chose and why): keep `IPhysics`'s API float, but ensure every caller always passes SHIP-RELATIVE small offsets (ship's double position subtracted from the target's double position, cast to float) rather than raw absolute coordinates - this mirrors the existing "camera-relative" render pattern applied to physics, and is a MUCH smaller change if it holds up under the acceptance test in item 6. Try this lighter-weight approach FIRST; only widen `IPhysics`'s own signatures to double if the relative-offset approach cannot cleanly cover every caller (e.g. because `query()`'s results need to be compared against other double-position things downstream in a way that loses precision through the float round-trip). Report which path you took.
4. **Update the precision-critical consumers identified in item 1's classification (a)** to use the new double accessor instead of the old float `position()`: `ship/gravity` (currently converts float `ship->position()` up to `world::Vec3d` for its own math - just call the new double accessor directly, this actually SIMPLIFIES that call site by removing a lossy round-trip), `ship/orbit_lock`, `ship/docking`, and the camera anchor (`core/camera` / wherever the render pose is published - trace it from `ship_core`'s pose through to `world/star_system`'s "camera position from the view matrix" recovery, and make sure that chain carries double precision end to end, not just at the two ends). Leave classification-(b) consumers on the existing float `position()` (do not need to change) UNLESS your audit in item 1 finds one that actually needs precision - if so, report it and treat it as classification (a).
5. **Regression-first testing (current scale, must be byte-identical in behaviour):** every existing test in `test_ship_core.cpp`, `test_gravity.cpp`, `test_orbit_guide.cpp`, `test_docking.cpp` (or wherever these live) must still pass unchanged - if any assertion needs updating because of a genuinely different (not just differently-typed) numeric result, STOP and report it, do not silently adjust a tolerance to make a real behaviour change pass. Add a new regression test that flies the ship through a normal scenario (thrust, orbit, dock) entirely within today's small-scale distances and confirms bit-for-bit / tolerance-for-tolerance identical results to before this change.
6. **New large-scale proof (this is the actual point of the task):** a scripted scenario (new dev flag if useful, e.g. `--precision-test` or reuse an existing scenario flag pattern) that teleports the ship to a LARGE distance from the origin - at least 10,000,000 (ten million) units, ideally higher if you have time to push it further toward realistic scale (billions), and then: flies under thrust for a while and confirms position integration stays smooth (no snapping/jitter - log position deltas per frame and show they stay proportional to velocity*dt, not becoming quantized), holds a `ship/gravity` orbit near a body placed out there and confirms it stays stable (reuse the existing `--gravity-scenario=orbit`-style verification approach, altitude/eccentricity staying sane over many simulated seconds), and confirms `ship/orbit_lock` and `ship/docking` still work correctly that far out (a lock still settles, a dock still holds within its normal tolerance). Report the actual before/after numbers proving THIS is what was broken and is now fixed (e.g. "at 5e9 units, the old float position drifted by ~500 units in one frame under 100 m/s thrust with zero input noise; the new double position drifts by the exact expected 100*dt with no error beyond double's own ~1e-6 relative precision").
