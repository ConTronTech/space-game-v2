CONTEXT: several modules already draw their own ad-hoc banners directly in ui/ship_hud (docs/HUD.md: orbit lock, docked/undocked, weapon overheated, cargo full, ore pickups...) - each one is bespoke code inside ship_hud.cpp/hud_logic.h. This task does NOT refactor those (too invasive to do unattended, and ship_hud's banners are tuned/tested); it builds the GENERIC version other future modules (and, later, ship_hud itself as a follow-up) can use, the same "optional service other modules opt into" pattern as core/debugger and core/profiler_overlay.

DESIGN: new module package/modules/ui/toast/ (name "ui/toast"; requires core/ui_handler). Provides core::IToast in toast_api.h:
- void show(const std::string& text, Level level = Level::Info, float seconds = 3.0f) where Level is an enum class { Info, Warning, Urgent } (three visual styles: calm/amber/red-flashing, matching the colour language already used everywhere else in this codebase - reuse existing RGB constants/conventions from hud_logic.h as a REFERENCE only, do not include that file, keep this module decoupled).
- Toasts STACK (a small vertical stack, newest at the bottom or top - pick one, document it) with a cap (toast.max_visible, default 4; more queue and appear as older ones expire), each fading out over its lifetime the same way existing banners already fade (linear alpha over the last ~0.5s), no per-frame allocation (fixed-capacity ring/array, cached text).
- Corner/position: pick a screen corner that does not collide with the existing HUD (ship_hud's banners live bottom-left/top-right already occupied by cargo/weapons/orbit/dock and the F3/F6 debug panels use their own corners: read docs/HUD.md and docs/DEBUGGER.md/docs/PERFORMANCE.md to see what is already using which corner, and pick the one that is clear, or a middle-top position if every corner is taken - document your choice and why).
- Tunables: toast.enabled (default true), toast.max_visible, toast.default_seconds. A dev flag --toast-test=TEXT[,LEVEL] that shows one toast at startup for screenshotting.

Pure logic in toast_rules.h (no GL/SDL/engine types): the stack/queue state machine (add, expire, cap overflow behaviour), fade alpha timing, layout (position of the Nth visible toast). Unit tests (tolerances): stacking order, cap/queue overflow, expiry, fade curve, level colours.
Docs: docs/TOAST.md (new: API, levels, positioning choice, how another module uses it - one example), docs/MODULES.md, docs/HUD.md (cross-reference: "the ad-hoc banners here are NOT yet using ui/toast; a future task could unify them").

OWNERSHIP: package/modules/ui/toast/** (new), tests (test_toast.cpp new, globbed), docs above. Do not edit ship_hud, game_menu, debugger, or any other module - this is a new, additive, standalone service that nothing else is wired to yet.

ACCEPTANCE: smoke + make test-san pass; screenshots (docs/WARP.md method, --toast-test) showing: one Info toast, stacked toasts of different levels (script several toasts via a repeatable dev-flag/scripted sequence if needed), an Urgent toast's flashing captured at two moments, the chosen screen position clear of other HUD elements (side-by-side with the normal HUD to prove no overlap).
